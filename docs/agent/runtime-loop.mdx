运行循环只负责“请求模型 → 处理工具调用 → 回填工具结果 → 再请求模型”

## 当前实现

当前 `agent/loop.ts` 使用单层循环，工具按模型给出的顺序串行执行。没有 Step 次数上限，也没有 `terminate`、`shouldStopAfterTurn`、steering 或 follow-up 接口；这些扩展设计见后文，不代表现有能力。

| 条件 | 当前结果 |
| --- | --- |
| 取消信号或模型 `aborted` | `cancelled`，不发起下一轮 |
| 模型流抛出异常 | 已取消则 `cancelled`，否则 `failed`，当前错误归为 `runtime` |
| 完整响应为 `error` 或携带错误 | `failed`，不执行其中的工具调用 |
| 无工具调用 | 发出 `turnCompleted`，运行 `completed` |
| 有工具调用 | 校验并逐个执行，回填工具结果，发出 `turnCompleted`，再请求模型 |

普通工具失败作为 `ModelMessage(role: "tool", isError: true)` 回填，允许模型在下一轮恢复。被截断或未注册的调用不执行，改为错误工具结果。

## 会话存储接入

Runtime 使用 Host 注入的 `SessionRecorder` 维护本次运行对应的持久化会话。Runtime 是用户消息、完整助手消息和工具结果提交顺序的唯一控制者；Host 负责创建 Recorder 并提供运行事件接收器。

用户消息提交顺序。

1. Host 创建 `runId` 并把已经绑定 `sessionId` 的 Recorder 注入 Runtime。
2. Runtime 创建一次用户 `ModelMessage`。
3. Runtime 等待 `commitUser` 完成本地提交。
4. Runtime 发出 `runStarted` 和 `turnStarted`，随后调用 Provider。

流式助手消息顺序。

1. `collectTurn` 消费 Adapter 的 `reasoning_delta` 和 `text_delta`。
2. Runtime 把每个增量同步交给 `recordAssistantDelta`，Recorder 更新内存草稿并调度合并写入。
3. Runtime 把相同的增量作为 AgentEvent 发给宿主，模型流、Recorder 和事件接收器分别维护自己的状态。
4. Adapter 的 `completed` 事件提供聚合后的正文、思考、工具调用和停止原因。
5. Runtime 构造完整 Assistant Message，并等待 `commitAssistant` 完成最终提交。
6. Runtime 把已经提交的 Assistant Message 加入本次运行的内存上下文，并发出 `assistantCompleted`。

工具结果提交顺序。

1. 带工具调用的 Assistant Message 完成本地提交。
2. Runtime 发出 `toolStarted` 并执行对应工具。
3. Runtime 根据 `ToolResult` 构造完整 Tool Message。
4. Runtime 等待 `commitToolResult` 完成本地提交。
5. Runtime 把已经提交的 Tool Message 加入内存上下文，并发出 `toolCompleted`。
6. 同一工具批次完成全部结果提交后，Runtime 发出 `turnCompleted` 并开始下一次模型请求。

终态提交顺序。

- 模型成功流包含一个 `completed` 事件。流结束时的终态检查把缺少 `completed` 的响应收敛为 `model_protocol` 失败。
- `completed` 事件直接承载工具调用时，`commitAssistant` 创建完成状态的助手记录。
- 取消和失败调用 `finishRun` 刷新活动草稿并提交终态，然后 Runtime 发出唯一的 `runCompleted`。
- 用户消息提交失败时，Runtime 直接收敛为 `failed`，Provider 保持待调用状态。
- Assistant Message 提交失败时，Runtime 直接收敛为 `failed`，工具保持待执行状态。
- Tool Message 提交失败时，Runtime 直接收敛为 `failed`，下一次模型请求保持待调用状态。

SessionRecorder 的数据结构、草稿刷新和本地事务以[会话存储](./memory.mdx)为准。AgentEvent 的身份和订阅契约以[运行事件](./events.mdx)为准。

## 后续扩展设计（尚未实现）

## `terminate` 的作用域

`terminate` 是每个工具执行结果上的可选控制元数据，不是 Agent 回合字段，也不是模型请求结果字段。Runtime 先为本回合的每个工具调用得到工具结果，再把这些结果聚合为一个工具批次状态：只有批次中存在调用且每个调用都明确要求终止时，批次才被视为终止。

因此：

- 单个工具调用带 `terminate: true`，表示这个工具批次不再自动请求下一轮 LLM；
- 多个工具调用时，必须每个调用都带 `terminate: true`，批次才关闭自动续轮；
- 一个调用为 `true`、另一个为 `false` 或未提供时，批次继续请求 LLM；
- `terminate` 不写入发送给模型的 `ToolResultMessage`，工具结果内容仍然保留并通过运行事件提供给宿主。

它表达的是“当前工具批次是否还需要模型接管”，不是“这个工具是否执行成功”。天气查询即使成功返回天气，也通常不设置 `terminate`，因为还需要 LLM 根据结果组织最终回答。

`terminate` 关闭的是自动工具续轮，并不保证整个 `run` 永远不可继续：如果 `shouldStopAfterTurn` 返回 `false`，随后读取到 steering message，或外层读取到 follow-up message，`pi` 仍可能再次请求 LLM。要在回合边界阻止这些宿主输入，应使用下面的 `shouldStopAfterTurn`。

## 可选的回合终止钩子

默认规则由模型输出决定，但 Host 可以注册 `shouldStopAfterTurn`：

`shouldStopAfterTurn` 接收当前 Assistant Message、该回合的所有工具结果、更新后的上下文和本次运行新增消息，并返回“继续”或“停止”的决定。

它在当前 Assistant Message、该回合全部工具结果和 `turnCompleted` 事件完成后调用，并且先于 steering / follow-up 队列检查；返回 `true` 时发出唯一的 `runCompleted` 并退出，不再读取或注入待处理消息，也不发起下一次模型请求。这个钩子适合上下文压缩失败、外部资源预算耗尽、宿主策略要求在当前回合收尾等明确条件，不应重新实现固定的 Step 计数上限。

钩子是“回合边界的优雅停止”，不是立即取消。用户点击停止或系统需要立刻终止模型 / 命令时，仍须调用同一个 `AbortSignal`。钩子本身应返回布尔值，不应通过抛出异常承担正常终止语义。

## 参考实现语义


steering 在当前回合结束后进入下一次模型请求，follow-up 在 Agent 原本要停止后重新开启外层循环。它们不是工具结果，也不改变 `terminate` 的批次计算；是否接收它们由 `shouldStopAfterTurn` 先行决定。

## 扩展后的运行顺序（尚未实现）

一次运行按以下语言顺序执行：

1. 用户发送任务，Runtime 创建本次运行的上下文并请求模型。
2. 模型返回普通正文或一个或多个工具调用。模型不直接返回 `terminate`。
3. 如果没有工具调用，当前 Assistant Message 成为候选最终回答；如果有工具调用，Agent 逐个或按调度策略执行它们。
4. 每个工具返回执行内容、成功或失败状态，以及可选的终止意图。Runtime 将同一模型回合中的工具结果聚合为工具批次状态，并保留所有结果。
5. 工具批次完成后发出回合完成事件，先询问 `shouldStopAfterTurn`。钩子返回“停止”时，不再读取 steering 或 follow-up，也不再请求模型。
6. 钩子允许继续时，Runtime 检查 steering 队列。队列有内容就将其加入上下文并请求下一轮模型；没有内容时，未终止的工具批次也会直接请求下一轮模型。
7. 当内层工具续轮结束后，Runtime 再检查 follow-up 队列。队列有内容就重新开始一轮模型请求；没有待处理消息时，运行自然结束。

`turnId` 和可选的 `turnOrdinal` 只用于事件关联和日志诊断，不参与 `while` 的退出条件或其他控制决策。

这套顺序解释了一个容易混淆的情况：`terminate=true` 会让内层“工具自动续轮”停止，但 steering 可以重新满足内层循环条件，follow-up 可以重新启动外层循环。只有 Host 钩子提前返回“停止”时，才会在当前回合后同时阻止这两类输入。

## 运行状态机

Agent 的运行状态在模型请求与工具执行之间切换，并最终收敛为 `completed`、`cancelled` 或 `failed`。宿主为每个 run 创建一个 `AbortController`，同一个 signal 同时传给模型请求和工具执行；Agent 观察到中止后不再发起下一轮，并发出唯一的 `runCompleted(status: "cancelled")`。

## 运行治理目标（尚未完整实现）

取消 Step 上限不等于取消运行治理：

- 用户始终可以停止运行；
- 模型调用与工具调用保留耗时、token、费用和错误诊断；
- 上下文接近模型窗口时由上下文管理策略压缩或产生明确错误，不能静默截断工具协议；
- 重复工具调用可以记录告警和观测指标，但不能未经产品策略授权就按固定次数终止；
- 权限拒绝、沙箱失败和系统资源错误通过 Tool Result 或 Run Error 明确表达。

当前已有共享取消信号、Bash 固定超时和结果截断；token / 费用统计、上下文压缩、重复调用告警尚未实现。上述目标不代替模型基于工具调用做出的任务完成判断。

## 验证矩阵

| 场景 | 预期 |
| --- | --- |
| 首轮只返回正文 | 一次模型请求后 `completed` |
| 首轮返回工具调用，第二轮返回正文 | 执行工具、回填结果、第二轮后 `completed` |
| 工具返回非零状态 | 作为错误结果回填，模型仍获得下一轮 |
| 模型请求失败 | `failed`，不执行消息中残留的工具调用 |
| 用户停止模型或命令 | `stopping → cancelled`，不发起下一轮 |
| 连续多轮工具调用 | 持续运行，不因 turn 数达到固定值而结束 |
| 用户消息提交失败 | `failed`，Provider 保持待调用状态 |
| 模型流结束时缺少 `completed` | `failed`，错误类型为 `model_protocol` |
| Assistant Message 提交失败 | `failed`，工具保持待执行状态 |
| Tool Message 提交失败 | `failed`，下一次模型请求保持待调用状态 |
| 纯工具调用响应 | 直接提交 completed Assistant Message，再进入工具执行 |
| 取消发生在助手流式输出期间 | Recorder 刷新草稿并提交 interrupted，随后发出 `runCompleted` |
