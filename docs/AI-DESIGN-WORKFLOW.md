# AI 软件前期设计工作法

> 版本：v1.0 · 日期：2026-08-27
> 用途：把一个软件从“想法”推进到“可以评审、可以实现的高保真原型”。

## 0. 核心原则

这套方法不按 PM、UX、UI 角色切分文档，而按设计决策和交付物切分：

```text
产品结构 → 交互逻辑 → 视觉设计 → 可交互原型 → 工程实现契约
```

每一层只回答一个问题：

- **产品结构**：软件里有什么？
- **交互逻辑**：用户怎么操作，系统如何响应？
- **视觉设计**：界面具体长什么样？
- **原型**：这些内容能不能被直接体验和评审？
- **工程契约**：这些行为如何稳定地实现？

不要把一份“页面行为说明”误认为完整 UX，不要把一份视觉稿误认为可用原型，也不要让原型自行发明产品范围。

## 1. 推荐目录结构

```text
docs/
├── product-structure/
│   ├── index.mdx
│   ├── main-workspace.mdx
│   └── settings.mdx
│
├── interaction/
│   ├── index.mdx
│   ├── main-workspace.mdx
│   └── settings.mdx
│
├── DESIGN.md
├── ENGINEERING-ARCHITECTURE.md
└── AI-DESIGN-WORKFLOW.md

docs/design/
├── README.md
└── components.md

designs/
└── <project-name>/
    ├── index.html
    ├── *.jsx / *.css
    └── screenshots/
```

`docs/` 放规则和说明，其中 `docs/design/components.md` 是按组件组织的视觉系统唯一源文件；每个组件章节自包含实际使用的颜色、字体、间距、尺寸、图标、状态和动效。`designs/` 放可以打开和操作的原型。

如果项目不需要单独的工程契约，可以暂时不创建 `ENGINEERING-ARCHITECTURE.md`；但一旦涉及 IPC、事件流、模型调用、权限或执行环境，就应该单独记录，避免混入交互文档。

## 2. 五类交付物的边界

### 2.1 产品结构（Product Structure）

产品结构是软件内容地图，不是行为逻辑。

它记录：

- 页面有哪些；
- 页面有哪些区块；
- 每个区块包含哪些内容、字段或能力；
- 哪些内容属于当前版本，哪些不属于；
- 数据安全或产品范围边界。

示例：

```md
---
title: 设置
icon: Settings
---

| 区块 | 内容 |
| --- | --- |
| 模型连接 | Provider、Model、Base URL、API Key |
```

不要在这里写“点击后进入某状态”或“按钮变成什么颜色”。那属于交互逻辑或视觉设计。

### 2.2 交互逻辑（Interaction Logic）

交互逻辑是“用户动作 → 系统响应 → 状态变化 → 用户反馈”。

示例：

```md
## 发送任务

1. 用户在底部输入区输入任务。
2. 用户点击发送或按 Enter。
3. 如果任务为空或没有工作目录，发送不执行，并就地说明原因。
4. 发送成功后创建新的 run snapshot，界面进入“连接中”。
5. 模型开始工作后显示进度摘要和执行详情。

## 停止任务

1. 运行中发送按钮变为停止。
2. 用户点击停止后进入“正在停止”。
3. 后端完成取消后显示“已停止”。
4. “已停止”与系统失败分开表达。
```

交互文档必须覆盖：

- 正常路径；
- 空状态；
- 加载和等待；
- 运行中；
- 用户主动取消；
- 系统错误；
- 重试和恢复；
- 键盘和焦点；
- 响应式窗口行为。

### 2.3 视觉设计（Design System）

视觉设计记录界面如何呈现，不重新定义产品内容和业务规则。

视觉规范按组件组织，而不是按颜色、图标或 token 类型拆分。每个组件章节都必须自包含：

- 颜色、字体和行高；
- 间距、尺寸、圆角和边框；
- 图标映射、尺寸、热区和无障碍标签；
- 默认、悬停、聚焦、禁用和运行状态；
- 动效、时长、缓动和 reduced-motion 规则；
- 深色/浅色或其他主题下的实际表现。

例如“设置入口使用 Settings 图标，18px，热区 40×40px，带 `aria-label="设置"`”属于视觉设计；“设置入口放在标题栏右侧，点击后打开右侧抽屉”属于交互逻辑。

### 2.4 可交互原型（Prototype）

原型是用来体验和评审的真实 HTML 页面，不是图片合集。

原型应当：

- 使用 `docs/design/components.md` 中对应组件章节的完整视觉契约；
- 显示关键页面结构；
- 能切换关键状态；
- 关键按钮至少有真实的原型行为；
- 能通过 HTTP 预览；
- 有清晰的演示入口，但不能把演示控制误认为产品功能；
- 对不属于当前版本的能力明确标注为禁用或不展示。

高保真原型可以先使用 mock data，但必须让评审者知道哪些是真实行为、哪些只是演示数据。

### 2.5 工程实现契约（Engineering Contract）

工程契约记录：

- 状态和事件如何传递；
- 哪一层负责模型、执行、权限和呈现；
- 取消、错误、流式事件如何贯通；
- 配置快照和运行身份如何关联；
- 安全边界和验证顺序。

前端不直接执行命令；模型决定工具调用，runtime 校验和编排，execution 执行，renderer 只呈现和发起意图。

## 3. 标准工作流程

### 阶段 0：项目现状审计

在写任何设计或代码前，先读取：

1. 项目目录和入口文件；
2. 产品文档和现有原型；
3. 前端组件、状态 store、事件协议；
4. 最近提交和工作区状态；
5. 现有截图或可运行页面。

记录三列：

| 事实 | 当前实现 | 目标/差距 |
| --- | --- | --- |
| 页面结构 | 顶部输入 + 右侧设置 | 底部输入 + 标题栏入口 |
| 运行状态 | running / done / error | running / stopping / cancelled / failed |
| 搜索 | 不存在 | 搜索当前 run |

规则：真实代码、事件协议和运行结果是“当前实现”的证据；截图只能证明视觉，不证明功能。

### 阶段 1：先解决范围冲突

常见冲突包括：

- 文档写了会话列表，但代码没有会话状态；
- 文档写了附件，但 IPC 没有附件通道；
- 原型画了设置抽屉，但产品范围只允许单次运行；
- UI 显示失败命令为成功。

遇到冲突时，不要直接补 UI。先确定唯一产品范围：

- 当前版本到底包含什么；
- 哪些能力是未来路线图；
- 哪一份文档是产品范围的来源。

### 阶段 2：写产品结构

每个页面先用表格描述内容，不写交互：

```md
---
title: 主工作台
icon: LayoutDashboard
---

| 区块 | 内容 |
| --- | --- |
| 标题栏 | 当前任务标题、运行状态、搜索、设置 |
| 消息流 | 用户任务、进度摘要、执行详情、最终回答 |
| 底部输入区 | 多行输入、发送 / 停止 |
| 设置抽屉 | Provider、Model、执行环境、工作目录 |
```

检查标准：读完后，别人能知道软件里有什么，但还不知道点击后会发生什么。

### 阶段 3：写交互逻辑

为每个重要动作写统一的五段式：

```text
前置条件 → 用户动作 → 系统响应 → 状态变化 → 用户反馈
```

至少列出：

- 空闲 → 发送；
- 发送 → 连接中；
- 连接中 → 运行中；
- 运行中 → 停止中 → 已停止；
- 运行中 → 完成；
- 运行中 → 失败 → 检查设置 / 重试；
- 搜索打开、输入、跳转、关闭；
- 设置打开、编辑、锁定、关闭。

交互逻辑要写“为什么”和“下一步能做什么”，不要只写视觉变化。

### 阶段 4：按组件建立视觉契约

逐个组件完成可独立实现的视觉章节：

1. 明确组件的内容、边界和布局结构；
2. 在同一章节写出实际颜色、字体、间距、尺寸和圆角；
3. 在同一章节写出图标语义、尺寸、热区、tooltip 和 `aria-label`；
4. 在同一章节写出默认、交互、错误、运行和完成状态；
5. 在同一章节写出动效时长、缓动和 reduced-motion 行为；
6. 最后补齐该组件在桌面、窄窗口和无障碍场景下的变化。

视觉系统的唯一文档源是 `docs/design/components.md`；实现代码可以使用 CSS 变量复用值，但不得再维护与组件章节平行的 token 或图标规范文件。

### 阶段 5：制作高保真原型

原型制作顺序：

1. 先做空状态和主工作台骨架；
2. 加入真实的底部输入和标题栏操作；
3. 加入设置抽屉和搜索浮层；
4. 加入运行、停止、失败、完成状态；
5. 加入展开执行详情、复制、重试等高价值交互；
6. 给每个高层页面加 `data-screen-label`；
7. 通过 HTTP 服务预览，而不是只打开截图。

对多文件 React/Babel 原型，使用固定版本的依赖和明确的脚本加载顺序；不要依赖 `file://` 加载多文件脚本。

### 阶段 6：浏览器验证和用户评审

验证顺序：

1. 页面是否加载；
2. 控制台是否有错误；
3. DOM 是否包含关键按钮、标签和可访问属性；
4. 关键点击和键盘路径是否可操作；
5. 375px、640px、900px 等宽度下是否可读；
6. reduced-motion 是否关闭装饰动画；
7. 让用户直接评审 live prototype，而不是只读文字。

原型评审中如果用户说“丑”“看不懂”或“像配置页”，先回到信息架构和视觉层级，不要马上只调颜色。

### 阶段 7：工程交接

交接顺序：

```text
产品结构 → 交互逻辑 → 事件/状态契约 → 视觉 token → 组件实现 → 测试
```

对于跨进程或异步 Agent 产品，先稳定状态语义和事件身份，再接流式、取消和错误恢复。不要在组件层用定时器伪造底层能力。

## 4. 质量判断标准

### 4.1 不是看改动大小

“改得少”不等于质量高。质量应看：

- 是否解决根因；
- 是否减少状态漂移；
- 是否提高用户理解和恢复能力；
- 是否让后续扩展更容易；
- 是否降低维护复杂度；
- 是否保留真实的安全和诊断边界。

必要时，重构状态边界比局部补丁更高质量。

### 4.2 每个设计决策必须可追溯

每个关键决策都应该能回答：

- 来源于哪个产品要求？
- 影响哪个交互状态？
- 由哪个 token 或组件表达？
- 由哪个工程层实现？
- 如何验证？

### 4.3 不把内部推理当稳定 UI 契约

Agent 产品可以展示进度摘要、工具调用和结果，但不要把模型内部 Thought 直接当成永久产品字段。产品应优先展示：

- 当前正在做什么；
- 已经完成什么；
- 结果是什么；
- 用户下一步能做什么。

## 5. 文档模板

### 5.1 产品结构模板

```md
---
title: <页面名>
icon: <文档图标>
---

<一句话说明页面用途，不写交互状态>

## 页面区块

| 区块 | 内容 |
| --- | --- |
| <区块> | <内容、字段或能力> |

## 当前版本范围

- <当前包含>
- <当前不包含>

## 安全/数据边界

- <敏感字段和数据范围>
```

### 5.2 交互逻辑模板

```md
---
title: <页面/流程> 交互
icon: <流程图标>
---

## <动作名称>

前置条件：<什么时候可以做>

1. 用户动作：<点击、输入、快捷键>
2. 系统响应：<加载、请求、事件>
3. 状态变化：<旧状态 → 新状态>
4. 用户反馈：<文案、焦点、错误、下一步>

## 边界状态

| 场景 | 系统行为 | 用户可做的下一步 |
| --- | --- | --- |
| <空状态/失败/取消> | <反馈> | <恢复动作> |
```

### 5.3 视觉 token 模板

```md
# <Component / Token>

## Token

- <名称>：<值>

## 状态

| 状态 | 外观 | 可访问性 |
| --- | --- | --- |
| default | <视觉> | <标签/焦点> |
| hover | <视觉> | <不依赖颜色> |
| disabled | <视觉> | <原因说明> |

## 使用边界

- <何时使用>
- <何时不要使用>
```

## 6. 可复制给其他 AI 的工作提示词

下面的提示词可以作为另一个 AI 的项目设计起始指令：

```text
你负责把一个软件从现状推进到可评审的高保真交互原型。

请使用以下四类交付物，不按 PM/UX/UI 角色拆文档：

1. product-structure：软件里有什么，包括页面、区块、字段和版本范围；不要写点击后的状态。
2. interaction：用户动作、系统响应、状态变化、反馈、错误恢复、键盘和响应式行为。
3. design：按组件组织颜色、字体、尺寸、图标、视觉状态和动效契约。
4. designs：使用前三者制作可打开、可点击、可评审的 HTML 原型。

工作规则：

- 先审计项目文件、真实前端状态、事件协议、现有原型和最近改动，再提出设计。
- 区分“当前实现”和“目标行为”；不要让截图或文档自行证明不存在的功能。
- 先解决产品范围冲突，再设计页面。
- 只问一个高影响问题一次；问题未解决时不要发明多会话、附件或历史数据。
- 先提出 2–3 个布局/交互方案，说明取舍和推荐方案。
- 在用户确认设计前，不写业务代码，不把视觉稿当实现。
- 原型必须使用 HTTP 预览，并检查控制台、DOM、键盘路径和窄窗口。
- 不用定时器伪造流式、取消或错误；这类能力必须在事件协议和状态机中解决。
- 最终回答优先于执行证据；执行详情可折叠但可搜索和审计。
- 不只依赖颜色表达状态；为图标按钮提供 aria-label、tooltip 和清晰焦点。
- 评价代码质量时看根因、状态边界、可维护性和用户体验，不以改动小为优点。

交付前请输出：

- 当前实现与目标差距；
- 产品结构文档；
- 交互逻辑文档；
- design token 与组件规范；
- 可交互原型路径和 HTTP URL；
- 浏览器验证结果；
- 尚未实现或需要用户确认的事项。
```

## 7. 最终检查清单

### 产品结构

- [ ] 能说清软件有哪些页面和区块。
- [ ] 没有把交互状态混进内容清单。
- [ ] 当前版本和未来能力边界明确。

### 交互逻辑

- [ ] 每个关键动作都有前置条件、响应、状态、反馈和下一步。
- [ ] 完成、失败、取消、上限、等待等状态有区分。
- [ ] 搜索、设置、停止和重试有闭环。

### 视觉设计

- [ ] 每个组件章节都自包含颜色、字体、间距、尺寸、图标和状态。
- [ ] 图标、尺寸、热区和 tooltip 有明确映射。
- [ ] 不依赖颜色表达唯一状态。
- [ ] 每个有动效的组件都有 dark mode、focus-visible 和 reduced-motion 规则。

### 原型

- [ ] 原型不是截图拼贴，而是可打开的 HTML。
- [ ] 关键操作可点击，状态可切换。
- [ ] HTTP 预览和控制台检查通过。
- [ ] 用户可以基于 live prototype 提出具体反馈。

### 工程交接

- [ ] Renderer、IPC、Runtime、Provider、Execution 的责任边界清楚。
- [ ] 事件有 run/step/action 身份，不依赖“最后一项”隐式更新。
- [ ] 取消、错误、流式和敏感数据边界有实现路径。
