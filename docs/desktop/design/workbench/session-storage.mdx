历史存储装配。

## 数据归属

- Main 使用 `app.getPath("userData")` 生成 `agent-sessions.sqlite`。
- `projects` 保存真实项目目录的稳定身份、规范化路径和最近激活时间。
- `entries.project_id` 保存项目历史范围；`NULL` 保存无项目历史范围。
- `project_context` 保存项目的优先排序、有界导航地图和省略元数据。
- 独立的待处理输入存储保存 Main 已接收的运行中补充文本及其应用状态；`entries` 保存 completed 用户消息与终态归档的 interrupted 用户输入。
- `HistoryRecorder` 保存当前历史范围的模型可见消息、流式草稿和工具恢复账本。
- Renderer 保存页面事件队列、项目展示状态和历史投影。

## 项目范围

应用初始使用 `projectId = NULL` 的无项目历史范围，Composer 显示 `Choose folder`。用户选择目录后，Main 规范化路径并查询 `projects.canonical_path`：已有记录沿用原 `projectId`，新目录创建新的项目记录。Main 将选中的项目范围作为当前历史范围，并加载对应的 `project_context`。

项目切换更新以下对象：

```text
active project descriptor
active HistoryRecorder(projectId)
active HistoryService(projectId)
active project_context
Canvas document route(projectId)
```

项目切换发生在运行空闲时。运行开始时，Runner 固定 `projectId`、`cwd`、HistoryRecorder 和项目上下文版本。
CanvasSurface 以项目 ID 加载对应场景，Main 以每次画布请求携带的项目 ID 派生文档路径；每个项目的写入队列按顺序提交其最新场景。

## 运行链路

1. Composer 提交任务、模型 ID、attachmentIds、canvasContextIds 和当前 `projectId`。
2. Main 校验项目范围，解析文件附件与 Canvas 选区引用，并从 `project_context` 取得有界目录上下文。
3. Main 创建或取得绑定当前 `projectId` 的 `HistoryRecorder`。
4. Runner 将文件路径提示并入当前任务，同时把选区 JSON 与项目上下文作为运行期消息交给 Runtime。
5. Runtime 读取 `HistoryRecorder.snapshot()`，追加运行期项目上下文、Canvas 选区 JSON 和当前用户消息。
6. Runtime 按提交屏障调用模型、工具和 Recorder。
7. Renderer 通过 AgentEvent 渲染实时过程，通过 `history:load-page` 读取当前范围的持久化历史。

## 运行中输入装配

1. Renderer 在当前模型输出或工具执行期间提交文本快照、独立 `inputId`、`activeRunId` 和当前 `projectId`；Preload 把 `steer` 请求交给 Main。项目、工作目录、模型、附件与画布选区继续使用 Runner 启动时捕获的配置。
2. Main 通过 Runner 核对活动 `runId` 与项目范围，其中 `projectId = null` 与项目运行使用同一接收契约。Main 在应用数据库中持久化待处理输入，并按接收顺序分配 `acceptOrder`。
3. 持久化完成后，Main 返回携带 `inputId`、`acceptOrder` 和接收时间的 ACK。ACK 表示 Main 已绑定并保存输入，`inputsApplied` 表示 Runtime 已把输入交给下一次模型请求。
4. Runtime 完成当前 Assistant Message 和已发起工具的全部 Tool Message 提交，在安全边界调用 Recorder。Recorder 在一个事务中按 `acceptOrder` 把本批输入写为 completed 用户 entries，并更新待处理状态；用户 entry 沿用 `inputId`。
5. Runtime 在事务完成后按顺序扩展内存 `messages`，发出 `inputsApplied` 并继续下一次模型请求。Renderer 依据 `inputId` 合并接收 ACK、应用事件与持久化 entry。
6. Runner 使用同一串行门控处理入队与终态封闭。门控内已接收的输入进入安全边界；封闭后收到的请求返回拒绝，发送方保留对应文本快照。停止、失败和启动恢复通过 Recorder 在事务中写入同 `inputId` 的 interrupted 用户 entries，并把剩余输入转为 `unapplied` 状态。

待处理输入以运行范围为归属，项目配置沿用运行启动时的快照；`projectId = null` 的终态输入记录进入通用历史范围。相同 `inputId` 的重试返回同一持久化接收记录，连续两条独立输入按 FIFO 处理。物理存储结构由实现确定，`entries` 的 `entryOrder` 继续表达 completed 消息的 Assistant、Tool、User 顺序，并保存 interrupted 用户输入的归档位置。

## 历史分页

`HistoryService` 保存一个 Main 侧当前范围读取器。Renderer 提交游标和页大小，Main 使用 `project_id = ?` 或 `project_id IS NULL` 读取 entries，并按照 `entry_order` 生成正序页面、下一页游标和 `snapshotOrder`。

Run 级时长以 `runStarted.startedAt` 为唯一计时起点，在运行终态计算总时长。HistoryRecorder 把总时长保存到最终 Assistant Message 的 `durationMs`；`runCompleted.finalTurnId` 与 `finalDurationMs` 提供最终回合身份和实时总时长，历史分页提供持久化时长。`inputsApplied.startedAt` 标记补充文本进入模型上下文的时刻。活动组时长归属见[消息流视图规范](./message-stream.mdx)。

HistoryService 继续分页 `entries` 并使用 `entryOrder` 游标。Renderer 以 `inputId` 归并运行 ACK、`runCompleted.unappliedInputIds` 和 completed/interrupted 用户 entries，并以项目范围和历史请求代次约束历史结果。

Preload 暴露：

- `getActiveProject()`；
- `selectProject()`；
- `clearProject()`；
- `loadHistoryPage()`。
- `steer()`：提交运行中补充文本并接收持久化 ACK。

Renderer 只能通过这些受限接口读取项目描述和当前历史页面。数据库路径、Repository 和其他项目历史范围由 Main 持有。

## 项目上下文

Main 以以下条件决定目录扫描：

- 项目第一次激活；
- 项目上下文缓存缺失；
- 扫描策略版本变化；
- 工具修改项目文件后缓存被标记 dirty。

每次项目范围的模型请求都取得缓存中的有界导航地图，以可读的工作目录说明和结构化目录行加入 transient `project_context`。地图标注深度、目录条目和总节点上限，并明确指出省略位置；文件正文由同一工作目录下的文件工具按需读取。目录地图不会进入 `entries`；Runtime 按本次运行固定的 `cwd` 提供文件操作上下文。

无项目范围拥有稳定的历史记录和模型上下文。它使用 `projectId = NULL`，以应用当前工作目录 `process.cwd()` 执行文件工具，并向模型提供该目录的简短说明；项目目录地图保持为空。文件工具注册独立于项目历史范围，因此无项目运行与项目运行使用相同的文件工具集。
